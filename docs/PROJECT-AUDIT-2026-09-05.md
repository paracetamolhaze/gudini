## Подтверждённые ошибки и недостатки

### 1. P1 — удаление проекта может затронуть каталоги за пределами загрузок

[Удаление в хранилище](C:/Users/almaz/Desktop/gudini/lib/store.ts:204), [маршрут DELETE](C:/Users/almaz/Desktop/gudini/app/api/projects/[id]/route.ts:33).

ID без проверки включается в путь и передаётся рекурсивному удалению, даже если такого проекта нет. Маршрутизатор Next декодирует закодированные разделители в параметре. Проверка в памяти с `id='../..'` и пустой БД направила удаление на корень проекта.

**Условия:** авторизованный запрос; при отключённой парольной защите доступ расширяется. **Исправление:** проверять формат ID и существование проекта, вычислять абсолютный путь, проверять его принадлежность каталогу загрузок до удаления.

### 2. P1 — публичная ссылка позволяет скачать исходную запись

[Исключение авторизации](C:/Users/almaz/Desktop/gudini/middleware.ts:33), [выбор исходника](C:/Users/almaz/Desktop/gudini/app/api/projects/[id]/video/route.ts:23).

Весь video endpoint публичный ради получения результата Instagram. Тот же endpoint поддерживает `which=raw`: получатель ссылки на готовое видео может запросить оригинал, включая вырезанные реплики. Знание идентификатора необходимо, но пароль от этого не защищает.

**Исправление:** исходники выдавать только после авторизации; для внешней платформы создавать отдельную временную подписанную ссылку на конкретный результат.

### 3. P1 — OAuth-подключение аккаунта не связано с начатой сессией

[Callback](C:/Users/almaz/Desktop/gudini/app/api/auth/[platform]/callback/route.ts:8), [начало OAuth](C:/Users/almaz/Desktop/gudini/app/api/auth/[platform]/route.ts:15).

Callback не проверяет одноразовый `state`; YouTube и Instagram не передают его при начале подключения. В изолированном вызове одного `code` оказалось достаточно для обмена и вызова `connectAccount`.

**Условия:** подставной код того же OAuth-приложения и переход уже вошедшего владельца по соответствующей ссылке могут привести к подключению чужого аккаунта. У TikTok есть дополнительный PKCE-механизм, поэтому его условия отличаются.

**Исправление:** случайный одноразовый state, связанный с браузерной сессией и платформой, срок действия и проверка до обмена кода.

### 4. P1 — повреждение JSON-базы становится тихой потерей проектов

[Чтение и запись БД](C:/Users/almaz/Desktop/gudini/lib/store.ts:146).

Единственный файл перезаписывается напрямую. После обрыва записи или заполнения диска он может стать неполным. Любая ошибка чтения трактуется как пустая БД; следующая запись закрепляет потерю старого списка. Это воспроизведено с подставной файловой системой. Аналогичный паттерн есть у настроек.

**Исправление сейчас:** отличать отсутствие файла от повреждения, прекращать запись при ошибке чтения, писать во временный файл с последующей атомарной заменой и хранить резервную копию. Далее — транзакционное хранилище и проверяемое восстановление. Сам по себе синхронный read-modify-write в одном Node-процессе не является доказательством гонки запросов.

### 5. P1 — первый сценарий создаётся без исследования фактов

[Создание проекта](C:/Users/almaz/Desktop/gudini/app/api/projects/route.ts:16), [перегенерация](C:/Users/almaz/Desktop/gudini/app/api/projects/[id]/generate/route.ts:23).

Обычное создание всегда вызывает `generateScript(topic)`. Исследование применяется только при перегенерации с отдельным флагом. Позже монтаж собирает research, когда пользователь уже прочитал сценарий, но записанные утверждения с ним не сверяет. Центральное обещание «сначала факты» не действует на основном пути.

**Исправление:** одна операция создания сценария для обоих маршрутов: исследование → достаточность фактов → сценарий с привязками. До съёмки показывать источники, спорные утверждения и связь чисел/имён с фактами.

### 6. P1 — разрешённая камера не разблокирует запись

[Получение потока](C:/Users/almaz/Desktop/gudini/app/project/[id]/page.tsx:349), [кнопка](C:/Users/almaz/Desktop/gudini/app/project/[id]/page.tsx:450).

Успешный `getUserMedia` меняет только ref. Перерисовки нет, поэтому кнопка сохраняет первоначальный `disabled`, пока пользователь не изменит другое состояние, например скорость текста. При ошибке камеры условие, наоборот, разрешает кнопку, чей обработчик ничего не делает без потока.

### 7. P1 — русское имя видео ломает загрузку до сетевого запроса

**Исправление:** безопасное ASCII-имя либо согласованное кодирование/декодирование. Добавить проверку имён с кириллицей. Отдельно сохранять запись до подтверждённой загрузки, чтобы сетевой сбой не лишал пользователя доступного дубля.

### 9. P1 — чистка может вырезать полезное предложение из импровизации

[Словарь](C:/Users/almaz/Desktop/gudini/lib/takeSelection.ts:66), [решение по ключевому слову](C:/Users/almaz/Desktop/gudini/lib/takeSelection.ts:294), [применение без общего лимита](C:/Users/almaz/Desktop/gudini/lib/speechCleanupRun.ts:63).

Слово «сначала» считается признаком разговора с монтажёром. Реплика вне найденных прочтений превращается в удаляемый `RETAKE` с уверенностью 1, без обязательного контекста дубля.

**Репродукция:** сценарий «Сегодня расскажем удивительную историю. Герой спас много жизней.»; речь «Это короткое вступление для зрителя. Сначала герой работал врачом. Потом произошла удивительная история.». При пословных интервалах 0.4 с и отключённой модели удалено всё предложение «Сначала герой работал врачом.» — 1.6 с, при нулевом совпадении со сценарием. Для точного прочтения совпадающего сценария такой результат не утверждается.

**Исправление:** обычное слово не должно доказывать служебную реплику. Требовать контекст дубля, сохранять неподтверждённую импровизацию и показывать пользователю удалённые фрагменты с возможностью возврата.

### 10. P1 — кэши исходника, распознавания и чистки не различают разные данные

[Кэш воркера](C:/Users/almaz/Desktop/gudini/worker/index.ts:69), [ключ ASR](C:/Users/almaz/Desktop/gudini/lib/pipeline.ts:109), [ключ чистки](C:/Users/almaz/Desktop/gudini/lib/pipeline.ts:163).

Воркер считает файл прежним по одному размеру. ASR дополнительно сравнивает округлённую длительность. План чистки добавляет только длину сценария и количество слов. Разные исходники одинакового размера, а также правки текста с сохранением длины могут использовать старую запись, транскрипцию или решения удаления.

**Исправление:** версия загрузки и хэш содержимого, хэш сценария/транскрипции, версия правил. Все производные артефакты должны хранить версии зависимостей; старые планы при восстановлении валидировать.

### 11. P1 — старое задание может завершить новый исходник чужим результатом

[Приём результата](C:/Users/almaz/Desktop/gudini/app/api/worker/complete/[id]/route.ts:29), [повторный запуск](C:/Users/almaz/Desktop/gudini/app/api/projects/[id]/process/route.ts:14), [интерфейс прогресса](C:/Users/almaz/Desktop/gudini/app/project/[id]/page.tsx:509).

Нет идентификатора попытки и версии входа. Сценарий: монтируется A → загружается B → A заканчивает → проект с B получает `done` и результат A. Завершение проверяет существование файла, а не принадлежность актуальной задаче. При аварийном завершении состояние может навсегда остаться `running`; API допускает повтор через 15 минут, но интерфейс скрывает кнопку.

**Исправление:** отдельный Job с ID, версией входа, сроком владения заданием и состоянием; проверять его при прогрессе, приёме частей и завершении. Старый результат не назначать проекту. Добавить отмену, истечение задания и доступный повтор.

### 12. P1 — написанные проверки готового видео не включены в основной запуск

В production вызывается технический `selfCheck`, затем устанавливается `done`. `checkRenderConformance` и `criticiseRender` не вызываются из пути сайта или воркера, хотя ARCHITECTURE описывает их как слои контроля. Наличие тестов этих функций не означает, что каждый готовый ролик проходит проверки.

**Исправление:** подключить бесплатную сверку результата с планом перед готовностью; хранить её отчёт и не пропускать непроверенные точки. Политику платного критика определить явно и отразить в статусе. «Файл исправен» и «содержимое проверено» должны быть различимы.

### 13. P2 — лимит и учёт расходов не изолированы по заданиям

[Проверка лимита](C:/Users/almaz/Desktop/gudini/lib/costLedger.ts:374), [глобальный ledger](C:/Users/almaz/Desktop/gudini/lib/costLedger.ts:89), [сброс при запуске](C:/Users/almaz/Desktop/gudini/lib/pipeline.ts:74), [транспорт ИИ](C:/Users/almaz/Desktop/gudini/lib/mediaLlm.ts:123).

Три связанные проблемы:

- `assertBudget` учитывает завершённые расходы, но не резервирует уже разрешённые запросы. Изолированно: лимит 1, два ещё не завершённых запроса по 0.8 оба разрешены, итог 1.6. Параллельные обращения уже используются в конвейере.
- Ledger и старые счётчики — общие переменные модуля. Одновременная обработка разных проектов на сервере допускается; запуск B сбрасывает накопления A. Это подтверждено на функциях учёта в отдельном процессе. Последовательность основного цикла воркера защищает именно этот его путь, но не параллельные серверные задания.
- Транспорт записывает usage после ответа SDK. Ошибка до ответа не создаёт запись попытки; SDK имеет собственные повторы, а поверх добавлен ещё один. Поэтому тест прямой записи `failed/retry` в ledger не подтверждает полноту реального транспорта. Неизвестную стоимость сбоя нельзя достоверно считать нулём.

**Исправление:** отдельный контекст каждого Job, атомарное резервирование бюджета до отправки, освобождение/уточнение после ответа, единая политика повторов и журнал каждой попытки. ASR также должен входить в предварительный контроль. Точные действующие тарифы требуют отдельной проверки у провайдеров.

### 21. P2 — состояние и настройки воркера расходятся с сайтом

[Синхронизация файлов](C:/Users/almaz/Desktop/gudini/worker/index.ts:41), [цикл заданий](C:/Users/almaz/Desktop/gudini/worker/index.ts:199), [определение доступности](C:/Users/almaz/Desktop/gudini/lib/workerState.ts:25).

У сайта и воркера разные тома. Музыка из настроек не синхронизируется; удалённое на сайте фото остаётся у воркера. При 404 фотографии функция возвращается до обработки шрифта. Изменения ключей на сайте не обновляют самостоятельную конфигурацию воркера.

Пока воркер занят долгим скачиванием, опрос jobs не выполняется, а отправка прогресса ещё не началась. После 90 с сайт может посчитать его выключенным и отправить следующий тяжёлый монтаж на веб-сервер.

**Исправление:** независимый сигнал доступности, состояния busy/offline, очередь и сроки владения заданиями. Версия применённой конфигурации; синхронизация добавлений и удалений файлов; явное отображение того, какие настройки использует воркер.

## Архитектура и организация разработки

**Сохранить удачные решения:** отделение решений ИИ от FFmpeg, явную политику провайдеров, preflight до оплаты режиссёра, кэш медиатеки с версиями QC, сохранение исходника, проверки реального рендера и fixtures речи. Они дают хорошую основу для исправлений.

**Выделить несколько конкретных границ внутри приложения:**

- `JobContext`: ID попытки, версии входов, состояние, отмена, расходы, резерв бюджета и артефакты. Это убирает общие счётчики и смешивание результатов.
- Сервис исследования/сценария: один контракт для создания и перегенерации.
- Хранилище версий медиа и производных результатов: хэш, статус полноты, происхождение, выбранная версия.
- Исполнитель заданий: сервер только ставит задачу и отдаёт статус, исполнитель отвечает за запуск/восстановление и лимит параллелизма.
- Проверка готового результата: обязательная операция, которую нельзя обойти отдельной кнопкой или маршрутом.
- Адаптеры публикации: платформенные состояния преобразуются в честную общую модель.

Для одного владельца разумный следующий шаг — транзакционное локальное хранилище метаданных и заданий, например SQLite, с продуманными резервными копиями. При нескольких серверах и пользователях понадобится общее серверное хранилище, например PostgreSQL, и отдельное хранение медиа. Выбор зависит от целевого развёртывания; на текущем этапе основная потребность — транзакции, версии и восстановление.

**Документация:** README обещает полный демо-цикл, а production V3 без исследования останавливается. PROJECT-OVERVIEW содержит описания старых fallback-провайдеров, типографики и публикации, рядом с новыми правилами. В ARCHITECTURE обязательные QC-слои не соответствуют графу вызовов. Историю решений лучше отделить от краткого актуального руководства; комментарии в коде обновлять вместе с изменением поведения.

**Проверки:** зелёные 186 тестов полезны, но часть тестов проверяет строки кода и вручную созданные структуры. Нужны проверки сценариев через реальные границы модулей: создание проекта до research; готовность камеры; кириллица; OAuth state; отказ API; восстановление после падения; замена исходника во время работы; независимость расходов; неподходящий кадр после refine; ошибка новой обложки. Сохранить уже существующие проверки FFmpeg. В рассмотренном дереве нет конфигурации GitHub Actions; внешние CI-проверки этим не исключаются.

**Деплой:** описание Docker предлагает `GUDINI_PASSWORD`, а сайт получает `SITE_PASSWORD`; отсутствие последнего отключает защиту. Не утверждается, что так настроен действующий сервер: значения окружения не проверялись. Для публичного режима требовать непустую однозначную настройку авторизации при запуске.

## Порядок работ

1. **Безопасность и сохранность:** запрет выхода из каталога при удалении, авторизация исходников, OAuth state, безопасная запись БД и проверка восстановления. Критерий: ошибочный ID, повреждение файла и чужой callback не меняют неподходящие данные.
2. **Основной путь пользователя:** камера, русские имена, создание сценария через исследование, честные статусы и обработка неуспешного сохранения. Критерий: весь путь проходит без обходных действий пользователя.
3. **Корректность монтажа:** защита импровизации, достоверный ASR, ключи кэша, сохранение границ пауз, релевантность после refine, аудио и подключение QC. Критерий: набор эталонных роликов сохраняет речь и совпадает с утверждённым планом.
4. **Устойчивое выполнение:** Job/inputVersion, отдельные каталоги попыток, heartbeat/восстановление, конфигурация воркера, изоляция расходов и резерв бюджета. Критерий: падение и повтор не смешивают версии и затраты.
5. **Развитие продукта:** ручная раскадровка, история обложек, повтор отдельных стадий, наблюдаемость и метрики результата. Начинать после стабилизации предыдущих пунктов.

Полезные метрики: доля роликов, завершённых без ручного вмешательства; число повторов и восстановленных заданий; время и стоимость каждой стадии; доля ошибочных вырезок речи; доля неверных кадров; процент QC FAIL; доля загрузок, дошедших до подтверждённой публикации. Целевые значения стоит задать после измерения небольшой контрольной серии роликов.
